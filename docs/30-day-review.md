# Thirty-day technical review

This is my checkpoint after the first 30 days of the project. It is a review of
what the repository can demonstrate, not a claim that a local portfolio replaces
production experience.

## What I built

The project now has one repeatable path from generated source files to tested
reporting outputs:

1. Python generates deterministic finance data from a fixed seed.
2. A shared source contract validates CSV headers before loading.
3. DuckDB replaces the raw batch atomically and keeps successful and failed run
   history separately.
4. dbt checks freshness, builds dimensions, facts and monthly marts, and retains
   observed plan and agreement history.
5. The subscription-payment fact handles late keys, corrections, source absence
   and reappearance through an incremental merge.
6. Run-level controls reconcile current and retained populations, while a separate
   view compares consecutive outcomes.
7. GitHub Actions runs the same complete `make verify` gate available locally.

## Evidence from the clean build

The fixed seed produces 25 customers, 25 loans, 20 subscription agreements, 99
loan payment attempts and 150 subscription billing attempts. The current build
passes:

- 11 table models, 2 incremental models, 1 view and 2 snapshots;
- 239 dbt data tests and 8 source-freshness checks;
- 256 dbt results including the checkpoint hook;
- 20 Python tests and Ruff; and
- four isolated scenario checks covering plan history, agreement history, source
  removal and six incremental payment states.

The payment scenario proves unchanged reruns, a late key, an in-place correction,
temporary source absence and restoration. Each of its six selected builds passes
55 results and records the resulting state and net difference from the preceding
run.

## Decisions I can explain in an interview

- Why grain is stated before measures and protected with uniqueness tests.
- Why completed collections are not described as recognised revenue.
- Why business event time is separate from the time a pipeline observes a change.
- Why source absence is retained but not labelled as a confirmed deletion.
- Why the incremental model uses a stable payment key and still reads the complete
  small source instead of claiming a performance improvement.
- Why current-state reconciliation, historical evidence and run-to-run differences
  answer different questions.
- Why failure records are committed separately from the transaction that replaces
  the raw batch.
- Why the first historical state is not manufactured into a change event and the
  first run comparison remains null.

## What this does not prove

This repository does not demonstrate production scale, cloud deployment,
multi-user concurrency, incident response or an external observability platform.
The synthetic sources are small; most marts still rebuild; the run audit lives in
the same DuckDB file; and there is no upstream extract identifier, deletion event,
retry service or alert routing. The AWS mapping in the architecture notes is a
design discussion, not a deployed system.

## Recruiter-facing assessment

The project now supports a credible statement that I understand and can implement
core analytics-engineering practices: reproducible transformation, dimensional
modelling, contracts, tests, reconciliation, history, incremental processing,
version control and CI. It complements my existing production work with Redshift,
AWS Glue/Python, Power BI, regulatory reporting and financial reconciliation.

It would be inaccurate to claim that this project alone proves senior data-platform
ownership. Its value is that the design choices and limitations are visible enough
to discuss and challenge in an interview.
